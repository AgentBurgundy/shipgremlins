# Dashboard design audit

**Component design review complete; publication remains gated on PR review and CI.** Reviewed on October 5, 2026 for version 0.19.0 on `codex/idea-foundation-environment`. Every dashboard script, stylesheet, page, and component family below received source review; the real browser pass covered their principal desktop/mobile surfaces and the interaction cases described here. This is not a claim that every external-service outcome was reproduced.

The requested scope is every dashboard page and component, including simple and advanced workflows. The design goal is a clear next action, one decision at a time, readable narrow layouts, and advanced controls that remain accessible without dominating routine work. A fresh idea must reach an approved foundation build before repository analysis or environment setup; established projects must make approved coding work easy to start.

Working evidence is in `.run/dashboard-redesign/`: `page-inventory.md`, `component-review.md`, `audit-records.json`, and matching screenshot `.png` / accessibility `.txt` files. These are local audit artifacts, not shipped documentation dependencies. This report indexes the browser operator's evidence; the independent source reviewer did not personally inspect every screenshot.

The preview denies outbound provider calls except an explicit fake Linear adapter. Repository creation, idea planning, worker execution, environment verification, and enrollment responses are synthetic. Review and foundation actions use the actual dashboard/API paths with these substituted boundaries. Remote enrollment returns an explicitly invalid preview command. No real repository, ticket, deployment, credential, worker enrollment, or agent run is created by those demonstrations.

## Findings repaired

- Sidebar and PM navigation overflow, tablet breakpoint conflicts, long headings, oversized checkboxes, and narrow form/action layouts.
- Primary collapsibles replaced with focused pages, tabs, and dialogs; concise project cards and knowledge excerpts; promotion controls separated from routine delivery review.
- Fresh ideas now build a foundation before PM analysis or hosting. Foundation inspection uses the configured base branch and rejects a provider's fallback branch.
- PM runs create missing Linear projects/labels and repair unambiguous proposal area labels; explicit mappings and approval remain protected.
- Direct coding launch and creative product exploration share existing runner, scope, budget, and review controls.
- Provider dialogs retaining stale tab ownership/labels, wrong settings sections, stale project fields after errors, and selected settings sections lost on save.
- Review evidence/focus lost during confirmation, dialogs opening at the bottom, missing top Close controls, duplicated raw setup metadata, and misleading ready-state guidance for projects with an existing crew.

## Verification and limits

Final local checks for 0.19.0: **1,884 Vitest tests passed, 6 skipped, 129 test files passed**; TypeScript, ESLint, repository formatting, 17 supplemental Node tests, configuration validation, and cron checks passed. Package smoke passed global CLI installation, packaged assets, controller lifecycle, staged activation/rollback, and preservation of configuration, queue, and context.

The browser used a disposable server with synthetic providers. Live OAuth, actual GitHub repository creation, live Linear repair, real coding execution, Vercel resource creation/deployment, and production promotion were not performed. Vercel prepared/deployed/canceled states and update/install error permutations received source/test coverage rather than new live browser execution. The running preview predates the final backend branch-inspection repair; its source-read regression tests and final package contain that repair.

Automatic foundation building currently supports a Node.js web app with npm. Source readiness checks for application files and commands; it does not establish that the app runs. Owners review the draft PR and its checks, then configure and verify browser access. The audit does not prove the creativity or commercial value of any model's future proposals.

## Publication gate

The design/component audit and local verification are complete. Publication still requires normal PR review and all four `hub-ci` jobs, followed by successful push CI for the exact merged `main` SHA. No recurring release job is needed or authorized.

The updater follows `main` and requires that exact SHA's successful push CI; a tag or GitHub Release alone is insufficient. The package is private and is installed from GitHub, not published to npm. Only after these gates should the verified commit be tagged, release notes published, and an authorized installation updated and checked. This report does not claim that publication or deployment has happened.
